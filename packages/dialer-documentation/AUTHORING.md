# Dialer documentation authoring

Write for reps first, administrators second, and integrators in Reference. A page should help its reader accomplish a task without requiring knowledge of the server's implementation.

The saved OS research is memory #16, **Research Bundle: Technical Writing video vT5pcc30Ffw**, source https://www.youtube.com/watch?v=vT5pcc30Ffw. Its applicable rules are plain language, detail matched to the reader, concrete definitions, ordered instructions, and notices placed before the relevant action. These are editorial guidance, not evidence that a product capability exists.

Use Start, Outbound, Inbound, Team, Analytics, Billing, Troubleshooting and Reference as the user-intent structure. Keep one canonical explanation and link to it rather than duplicating it across sections.

A task page should state the result, prerequisites, shortest correct sequence, expected state and recovery path. Explain the simple model before exact vocabulary. Separate user instructions from SDK/HTTP reference and scientific background.

## Evidence and availability

Maintain CLAIM-LEDGER.md. Allowed states are shipped, preview, planned, unresolved and deprecated. Current pages are preview. Do not advertise a planned feature as available. A carrier answer differs from a human connection; an accepted offer differs from confirmed media; UI presence differs from ready capacity.

Use actual catalog and live billing evidence for prices. Do not copy test-fixture prices or claim unlimited usage because a field is null. Live coaching and uploaded-transcript feedback remain planned unless implementation and runtime evidence are added.

Keep existing short-landscape, mobile menu, desktop sidebar, theme, search, keyboard and Markdown behavior. Validate content links and rendered interactions rather than adding tests that merely repeat prose.
