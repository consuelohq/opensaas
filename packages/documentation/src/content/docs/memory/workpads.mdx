A **workpad** is the running record for one scoped task. It keeps the decisions and proof that are easy to lose when work spans many tool calls or changes agents.

The scoped workpad path is:

```text
.task/<area>/<task-slug>/workpad.md
```

Some older lifecycle paths still recognize `.task/workpad.md`; the task metadata determines which workpad belongs to the active branch.

## What belongs in a workpad

A useful workpad carries the task's acceptance criteria, plan, current status, files changed, key decisions, issues and recovery notes, and validation evidence. Engineering tasks also record a `Test-first contract` and red/green/post validation evidence when that workflow applies.

The point is not to produce a diary. The point is to keep the smallest durable record that lets another agent understand what is being changed, why, and how the result was proven.

## How it stays current

The task lifecycle updates workspace-owned workpad sections as files are read or changed and as validation runs. Agent-authored sections remain the place for intent, decisions, discoveries, and follow-ups.

Before publish, the workflow checks that the workpad has a meaningful agent-authored update. A stale starter workpad is treated as incomplete.

## How a workpad gets saved

`task.push` publishes the task changes and also attempts to save the workpad as durable memory with the `workpad` category. That memory write is **best-effort**: a memory-service failure should not make an otherwise valid code push fail.

This gives the same task two useful forms of persistence:

1. the workpad file in the task worktree while the task is active;
2. a saved workpad memory that stream context can retrieve later for another agent.

Because workpads are saved with branch/task identity, `stream.context` can surface recent workpads for the same area instead of forcing the next agent to reconstruct state from commits alone.

Implementation evidence: `packages/os/scripts/lib/task-workpad.js` and `packages/os/scripts/task-push.js`.
