Access in Consuelo OS is the intersection of identity, workspace, app, caller, route, and scope. Passing one check never skips the others.

## What a protected caller is bound to

A current agent or app credential can be bound to:

- a workspace;
- a subject and device;
- a connector and connection;
- a caller and app;
- an explicit set of scopes;
- an expiry and credential status.

The local gateway compares those claims with the request. A valid signature for the wrong workspace, caller, app, device, connector, or connection is rejected.

## Scopes answer one question

A scope says which operation the caller may request. MCP read operations use a route scope such as:

```text
route:/mcp:read
```

Tool calls use a scope derived from the current tool manifest. The gateway does not guess that an unknown tool is harmless: an **unknown tool** has no valid classification, returns `UNKNOWN_TOOL_SCOPE`, and must **fail closed**.

Scopes can be exact or deliberately broader where the current grant model supports a wildcard. Grant the narrowest useful set and rotate the credential when its job changes.

## Permission tiers

Tool and skill manifests classify side effects independently of caller identity.

| Tier | Meaning | Normal approval posture |
| --- | --- | --- |
| `read` | Read existing workspace or connected data | Usually no action approval |
| `draft` | Create a proposal without committing the downstream write | Approval before commit |
| `write` | Change workspace records or files | Approval unless policy explicitly grants it |
| `execute` | Run a process or workflow | Depends on side effects |
| `external` | Affect an outside system or person | Approval required |
| `admin` | Change secrets, permissions, deployment, billing, or system state | Approval required |

The permission tier describes the action. The scope describes what this caller may request. The approval rule decides whether the action may proceed now.

## Route access is separate

The workspace route registry currently supports four route modes:

- `public` for an intentionally public surface such as an approved static snapshot;
- `required` for a route that must authenticate before use;
- `workspace-session` for a signed-in workspace browser session;
- `signed-connector` for an internal hop carrying platform-generated request proof.

A public route is not a public tool grant. The route target still determines whether the response is a static object or a live protected service.

## Dangerous input is rejected early

The local server checks destructive command material before normal tool dispatch. Catastrophic shell patterns are blocked without echoing the raw payload into the event record. Ordinary prose and permitted calls continue through the normal manifest and approval checks.

## Review access safely

When a caller is denied, inspect the stable error and required scope. Do not broaden every credential or disable the guardrail to make one call pass. Confirm:

1. the intended workspace and app;
2. the exact route or tool;
3. the required scope;
4. the permission tier;
5. whether action approval is required;
6. whether the credential should be rotated instead of expanded.
