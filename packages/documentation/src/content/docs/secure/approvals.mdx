Consuelo uses approval at two different moments. **Connection approval** decides whether a device or client may join a workspace. **Action approval** decides whether one sensitive operation may execute. They are not interchangeable.

## Device and workspace approval

A normal local setup creates a device request with a local **device public key**. The browser flow requires **stronger authentication**, then binds the approved bootstrap to the matching device proof.

Current hardening rejects:

- device-code creation without a local public key;
- anonymous or forged browser approval;
- redemption without the matching device proof;
- plain username and password as the approval method.

After identity approval, the user may need to select or create the workspace. The control plane registers the workspace, node, route, and connector state before committing the final approval. If route or connector provisioning fails, the install receives a terminal failure instead of a half-approved public route.

## Connection approval grants a boundary, not every action

Approving a node establishes who and what belongs to the workspace. It does not approve all future writes, external messages, commands, or administrative changes.

The resulting client still receives scoped credentials. Every protected request still passes route, identity, signature or bearer, scope, and tool-policy checks.

## Action approval

An **action approval** happens immediately before higher-impact work. Current manifests and local guardrails can require it for:

- writes outside the Consuelo home;
- shell execution with side effects;
- external communication or API changes;
- administrative configuration, credentials, deployment, or billing;
- skills explicitly marked `requiresApproval: true`.

Some destructive command material is blocked rather than offered for approval.

Current skill execution returns `APPROVAL_REQUIRED` before running. It does not keep a hidden process waiting indefinitely. After review, use the supported approved path or rerun with the required authorization.

## A useful approval request

State:

1. the exact action;
2. the target workspace, file, service, or recipient;
3. the expected side effect;
4. the evidence already checked;
5. how success will be verified;
6. how the change can be reversed, when reversal is possible.

Avoid vague requests such as “approve admin access.” Approve the smallest action at the decision point.
