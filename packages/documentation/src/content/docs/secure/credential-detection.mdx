Credential detection answers one narrow question: **can the local adapter resolve the configuration it needs?**

A detector should report states such as:

```json
{
  "provider": "example",
  "credential": "api-key",
  "status": "present",
  "source": "apple-keychain"
}
```

or:

```json
{
  "provider": "example",
  "credential": "api-key",
  "status": "missing"
}
```

It must not return the API key, token length, prefix, last characters, hash, or another fingerprint that makes correlation easier.

## Detection does not grant permission

A `present` result does not grant permission to invoke a provider tool. Tool discovery, caller scope, provider account selection, approval policy, and the provider’s own permissions still apply.

The safe sequence is:

1. detect `present` or `missing`;
2. resolve the intended provider account or project;
3. run one bounded read-only check;
4. authorize the exact tool method;
5. request approval before a write.

## Ask your agent

```text
Add a provider configuration check that reports only present, missing, or invalid.
Do not return the secret, a prefix, suffix, length, hash, or command output containing it.
Keep credential detection separate from tool authorization and action approval.
Test missing, valid, invalid, and provider-denied states.
```

## Environment variables

A local process may also receive a credential through an environment variable. The detector may report `source: environment`, but it should not read or print the value for diagnostics. Avoid putting secrets in shell history, process arguments, `.env` files committed to Git, traces, or screenshots.
