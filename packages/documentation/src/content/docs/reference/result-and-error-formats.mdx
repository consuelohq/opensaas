Consuelo uses structured envelopes so callers do not have to infer success from terminal text.

## `ToolResult`

Facade tools return:

```json
{
  "now": "2026-07-13T23:00:00.000Z",
  "ok": true,
  "code": "OK",
  "message": "command completed",
  "data": {},
  "stderr": "",
  "exitCode": 0,
  "durationMs": 42,
  "traceId": "trc_123",
  "apiVersion": "1.0.0"
}
```

Optional fields are `requestId`, `inputTokens`, `outputTokens`, `totalTokens`, `detail`, and `changed`.

| Field | Contract |
| --- | --- |
| `ok` | Boolean success signal. |
| `code` | Stable machine-readable facade code. |
| `message` | Short human-readable summary. |
| `data` | Tool-specific structured result. |
| `stderr` | Captured standard error, empty when absent. |
| `exitCode` | Underlying process status, normally `0` on success and `1` on failure. |
| `durationMs` | Measured tool duration. |
| `traceId` | Trace identifier for correlation. |
| `apiVersion` | Current envelope version, `1.0.0`. |

Current facade codes are:

- `OK`
- `VALIDATION_ERROR`
- `AMBIGUOUS_TASK_SELECTION`
- `WORKTREE_NOT_FOUND`
- `COMMAND_FAILED`
- `TIMEOUT`
- `PARSE_ERROR`
- `NOT_FOUND`
- `TASK_SESSION_NOT_FOUND`
- `TASK_SESSION_REQUIRED`
- `DRY_RUN`

A failed result can still contain useful `data` and `stderr`. Branch on `ok` and `code`, not on whether text is empty.

## `CallOutput`

OS skills return a different envelope:

```json
{
  "ok": true,
  "name": "sites",
  "permission": "guidance",
  "traceId": "trc_456",
  "durationMs": 18,
  "result": {},
  "artifacts": [],
  "proposedWrites": [],
  "requiresApproval": false
}
```

On failure:

```json
{
  "ok": false,
  "name": "example",
  "permission": "execute",
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Input did not match the skill schema.",
    "details": {}
  }
}
```

`permission` is one of `guidance`, `read`, `draft`, `write`, `execute`, `external`, or `admin`. `artifacts`, `proposedWrites`, and `requiresApproval` appear only when relevant.

Skill error codes are subsystem-specific and are not one closed global enum. Treat `error.code` as the machine key and preserve unknown future values.

## MCP result wrapping

MCP `tools/call` wraps the visible skill result as JSON text:

```json
{
  "content": [
    { "type": "text", "text": "{\n  \"summary\": \"...\"\n}" }
  ],
  "isError": false
}
```

Transport and JSON-RPC errors can occur before a `CallOutput` exists. See [MCP](/reference/mcp/) and [Security reference](/secure/security-reference/).

## HTTP route errors

Local JSON routes generally return:

```json
{
  "ok": false,
  "error": {
    "code": "SOME_ERROR",
    "message": "Safe public message."
  }
}
```

Use the HTTP status for transport outcome and `error.code` for program logic. Do not expose raw internal exception text to end users.

## Node-routing errors

Workspace routing can fail before the selected node executes a tool. Current routing errors include:

| Code | Meaning |
| --- | --- |
| `WORKSPACE_NODE_OFFLINE` | The exact node required for the route is not currently reachable. |
| `NODE_ROUTE_MISMATCH` | Multiple node-routing hints conflict, so Consuelo refuses to guess. |
| `TASK_NODE_MISMATCH` | An explicit node conflicts with the node that already owns the task session. |

These failures are intentionally fail-closed. In particular, task-owned work is not silently sent to another healthy node just because its owner is offline. See [Routing work](/nodes/routing/).
