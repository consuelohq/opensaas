A facade tool is a typed operation exposed through the workspace tool facade. The generated full manifest marks these entries with `kind: "facade-tool"`.

## Definition fields

| Field | Type | Meaning |
| --- | --- | --- |
| `name` | string | Stable dotted tool name such as `fs.read`. |
| `methodPath` | string[] | Facade method segments. |
| `description` | string | Intent and operating boundary. |
| `category` | string | Discovery category. |
| `underlying` | string | Backing subsystem or script. |
| `capabilities` | object | Read, mutation, determinism, and retry metadata. |
| `defaultTimeout` | positive integer | Default execution timeout in milliseconds. |
| `inputSchema` | string | Name of the validated input schema. |
| `outputSchema` | string | Name of the result schema. |
| `command` | object | Script and argument mapping used by the executor. |
| `exampleInput` | object | Minimal valid example for discovery. |
| `sessionRequired` | boolean, optional | Whether a task session is mandatory. |

Tool names follow `^[a-z][a-zA-Z0-9]*(\.[a-z][a-zA-Z0-9]*)*$`.

## Capability metadata

```json
{
  "readOnly": true,
  "mutating": false,
  "deterministic": true,
  "safeToRetry": true
}
```

- `readOnly` and `mutating` describe side effects.
- `deterministic` describes whether equal input and state should produce equal output.
- `safeToRetry` describes whether an automated caller may retry without duplicating an unsafe effect.

Do not infer `safeToRetry` only from `readOnly`; use the declared value.

## Command mapping

The `command` object can declare:

```json
{
  "script": "code-call",
  "subcommand": "run",
  "branchMode": "required",
  "branchArgumentStyle": "flag",
  "jsonFlag": "--json",
  "dryRunFlag": "--dry-run",
  "arguments": [
    { "source": "path", "flag": "--path", "kind": "value", "required": true }
  ]
}
```

`branchMode` is `none`, `optional`, or `required`. Argument kinds are `value`, `boolean`, `array`, `record`, or `commandArray`.

## Call shape

Agent clients call the facade with a tool name and typed input. Task-scoped operations also put `taskSession` at the call envelope's top level.

```json
{
  "tool": "fs.read",
  "input": {
    "path": "README.md",
    "offset": 1,
    "limit": 80
  },
  "taskSession": "tsk_123"
}
```

The facade validates input before executing the backing command. It returns a `ToolResult`, not unstructured terminal prose.

The call envelope also supports a top-level `workSession` for work-session node routing. `taskSession` and `workSession` are mutually exclusive. Adding work-session routing does not by itself grant a tool new filesystem mutation authority: a tool must explicitly support work-session execution before it can use that session for work.

## Starting sessions

`session.start` is the canonical session constructor. `kind: "task"` delegates to the existing task lifecycle and returns `sessionKind: "task"`, `taskSession`, `taskBranch`, and `worktreePath`; `task.start` remains available as a compatibility alias. `kind: "work"` creates metadata only for an existing directory and returns `sessionKind: "work"`, `workSession`, `ownerNodeId`, and `path`. It does not create a branch, worktree, PR, or copied directory.

```json
{
  "tool": "session.start",
  "input": {
    "kind": "work",
    "path": "/Users/me/Developer/raycast-extension"
  }
}
```

## Subagents

`subagent` starts or attaches to durable Codex and Grok runs from an instruction handoff. The default tool deadline is 15 minutes so deep reviews can complete without disabling bounded execution. A `start` or bounded `wait` response for a run that is still `starting` or `running` reports `exitCode: 0`; use the returned run `status` to distinguish active work from terminal completion. Provider capability limits remain explicit—for example, Grok rejects unsupported `reasoningEffort` selection instead of silently ignoring it.

## Operator releases

`release` is the canonical Consuelo OS operator release tool. Given a GitHub PR, it verifies the PR is ready for `main`, merges it, waits for the runtime publication associated with that exact merge SHA, promotes the exact immutable bundle through the requested release channel, and by default updates the current operator node to the exact released version and verifies the installed bundle. Use `releaseOnly: true` when the release should stop after channel promotion.

```json
{
  "tool": "release",
  "input": {
    "pr": 2185,
    "channel": "canary"
  }
}
```

The tool is intentionally discoverable for requests such as “release,” “deploy this PR,” “release to canary,” and “release and update.” It keeps GitHub environment approvals, release signing, immutable-bundle verification, and channel transition rules in the existing protected workflows; it never returns release credentials.

## Maintenance and observability examples

The full manifest can expose higher-level maintenance operations in addition to file and task primitives:

| Tool | Behavior |
| --- | --- |
| `security.scan` | Runs a defensive scan of the current Git repository with the configured Bun audit, OSV-Scanner, Trivy, and Semgrep binaries. It returns normalized findings, scanner status, local evidence paths, cross-scanner groups, and new/persistent/resolved deltas. It does not accept a remote host target. |
| `monitor.errors` | Reads the last 24 hours of the canonical Consuelo tool-trace database and compares failures with the current tool contract. Expected policy enforcement and caller-input errors remain distinct from drift, transient failures, external failures, and defect candidates. |
| `dailySchedules.publish` | Explicitly publishes a dated security scan or maintenance workpad into the private artifact archive and refreshes the Daily Schedules index. Existing entries use artifact version concurrency rather than an unconditional overwrite. |

`security.scan` and `monitor.errors` are read surfaces. Publishing a durable Daily Schedules entry is a separate mutating operation so callers can inspect evidence without creating an artifact as a hidden side effect.

## Node and session routing

When a workspace has more than one node, the OS routing layer can resolve a facade call from task ownership, work-session ownership, an explicit node target, or the workspace default. Task-scoped operations put `taskSession` at the call envelope's top level; work-session calls use `workSession` instead.

Do not assume that changing the default node moves an active task. A successful `task.start` binds that session to the node that started it; follow-up calls carrying the session keep using that owner until the task affinity is successfully released.

A successful `session.start` with `kind: "work"` similarly binds the returned work session to the node that created it. Central routing stores the session-to-node affinity, while the work-session path remains local to the owner node.

See [Routing work](/nodes/routing/) for user-facing behavior and [Result and error formats](/reference/result-and-error-formats/#node-routing-errors) for mismatch and offline failures.

## Discovery

Use `get_steering` for the core surface and `tools.search` for everything else. `tools.search` can filter by category and read/mutation intent. The generated core manifest is intentionally smaller than the full manifest.

## Effective availability

Installed does not always mean enabled. Settings overlays can remove a facade tool from the effective manifest. Authorization and approval policy can still block a tool that remains discoverable.
